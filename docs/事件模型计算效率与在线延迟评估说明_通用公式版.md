# 事件模型计算效率与在线延迟评估说明

## 1. 问题背景

目前论文主要使用 runtime 比较不同方法的模型效率。然而，事件视觉方法的输入组织方式差异很大，一次模型推理所对应的感知数据并不相同。例如：

- EV-SpSegNet 一次处理完整的 8 s 事件流；
- HLC² 将 8 s 事件流划分为多个固定时长窗口，并按窗口连续处理；
- RVT 和 SAST 通常处理由 50 ms 事件构建的 voxel representation；
- CETUS 根据事件率动态调整一次处理的事件数量和时间跨度；
- 部分异步图网络甚至在新事件到达时逐事件更新。

因此，“一次 forward 需要多少毫秒”并不是一个具有统一含义的比较指标。一次 forward 可能对应 8 s、400 ms、50 ms，或者数量可变的一小批事件。直接比较这些数值，会把下面两个不同问题混在一起：

1. **计算吞吐效率**：模型处理一段固定长度的事件流需要多少计算时间？
2. **在线响应能力**：一个事件发生以后，系统多久能够输出包含该事件的预测？

这两个问题都与模型效率有关，但衡量的系统属性不同。前者关注“处理完整工作负载的速度”，后者关注“系统对新信息作出反应的速度”。

---

## 2. 计算吞吐效率：处理完整事件流需要多久？

### 2.1 直观定义

计算吞吐效率回答的问题是：

> 给定相同长度的事件流，例如一个 8 s 测试样本，不同方法分别需要多少计算时间才能完成全部预测？

一段事件流的总处理时间可以表示为：

$$
T_{\mathrm{stream}}
=
T_{\mathrm{rep}}
+T_{\mathrm{transfer}}
+\sum_{m=1}^{M}T_{\mathrm{forward}}^{m}
+T_{\mathrm{post}}.
$$
其中：

- $T_{\mathrm{stream}}$：处理完整事件流的总时间；
- $T_{\mathrm{rep}}$：构建模型输入表示的时间，例如生成 event count、event frame、voxel grid，或者划分 point windows；
- $T_{\mathrm{transfer}}$：数据从 CPU 传输到 GPU 的时间；
- $M$：处理完整事件流所需的模型更新次数；
- $T_{\mathrm{forward}}^{m}$：第 $m$ 次模型推理的时间；
- $T_{\mathrm{post}}$：预测拼接、阈值处理等后处理时间。

公式中的求和符号表示：一个完整样本不一定只进行一次 forward。以 HLC² 为例，一个 8 s 样本在 400 ms 窗口设置下包含 20 个窗口，因此需要连续执行 20 次模型更新。

### 2.2 HLC² 的具体例子

当前实验中，HLC² 处理一个完整 8 s EV-UAV 样本需要 190.14 ms。这个数值表示：

> HLC² 完成该样本中 20 个窗口的输入处理、模型推理和预测输出，总共需要约 190.14 ms。

如果当前计时范围确实覆盖公式中的所有步骤，那么：

$$
T_{\mathrm{stream}}=190.14\ \mathrm{ms}.
$$
它对应的 real-time factor 为：

$$
\mathrm{RTF}
=
\frac{\text{事件流的真实时长}}
{\text{处理该事件流所需的计算时间}}
=
\frac{8000}{190.14}
\approx 42.1.
$$
也就是说，HLC² 的计算速度约为实时事件流产生速度的 42.1 倍。这个结果能够说明模型具有较高的离线吞吐率，并且处理速度足以跟上实时事件流。

但是，190.14 ms **不是目标事件出现后获得预测所需的在线响应时间**。它是处理完整 8 s 样本的总计算时间。

### 2.3 这个指标适合比较什么？

在所有方法接收相同 8 s 原始事件流、执行相同输出任务并采用一致计时范围的前提下，$T_{\mathrm{stream}}$ 可以公平比较：

- 处理相同感知时长所需的总计算成本；
- 单位时间内能够处理多少事件；
- 模型是否能够以实时速度持续处理事件流；
- 不同方法的总体计算吞吐率。

因此，当前 runtime 实验并非没有价值。更准确的名称应当是：

> **Processing time (ms / 8-s stream)**

而不宜直接将其称为 online latency。

## 3. 在线响应延迟：一个事件多久后能获得预测？

### 3.1 直观定义

在线响应延迟回答的问题是：

> 一个事件在传感器中发生以后，经过多长时间，系统才能输出包含该事件的预测结果？

它可以表示为：

$$
L_{\mathrm{response}}
=
L_{\mathrm{accumulation}}
+L_{\mathrm{queue}}
+T_{\mathrm{rep}}
+T_{\mathrm{transfer}}
+T_{\mathrm{forward}}
+T_{\mathrm{post}}.
$$
其中：

- $L_{\mathrm{response}}$：从事件发生到对应预测可用的总延迟；
- $L_{\mathrm{accumulation}}$：等待足够事件构成一次模型输入的时间；
- $L_{\mathrm{queue}}$：等待上一轮推理结束的排队时间；
- $T_{\mathrm{rep}}$：将当前事件转换成模型输入表示的时间；
- $T_{\mathrm{transfer}}$：将数据传输到计算设备的时间；
- $T_{\mathrm{forward}}$：本次模型推理时间；
- $T_{\mathrm{post}}$：得到最终可用预测的后处理时间。

这里最容易被忽略的是 $L_{\mathrm{accumulation}}$。即使模型 forward 只需 5 ms，如果模型必须先收集 400 ms 的事件，那么窗口开始阶段出现的事件仍然需要等待接近 400 ms。

### 3.2 固定时间窗口中的事件等待时间

假设模型每收集一个时长为 $W$ 的事件窗口后执行一次推理：

- 窗口开始时出现的事件需要等待接近 $W$；
- 窗口结束前出现的事件几乎不需要等待事件积累；
- 如果事件在窗口内大致均匀分布，平均积累等待时间约为 $W/2$；
- 最长积累等待时间接近 $W$。

在暂时忽略排队、表示构建和数据传输的情况下，可以近似写成：

$$
L_{\mathrm{mean}}
\approx
\frac{W}{2}+T_{\mathrm{forward}},
$$
$$
L_{\mathrm{max}}
\approx
W+T_{\mathrm{forward}}.
$$
这里的 $L_{\mathrm{max}}$ 指窗口开始阶段事件的近似响应延迟，而不是所有事件都必须等待完整窗口时长。

### 3.3 HLC² 在 400 ms 设置下的例子

一个 8 s 样本包含 20 个 400 ms 窗口。根据当前完整样本 runtime，可以粗略估计每次更新的平均计算时间：

$$
\overline{T}_{\mathrm{update}}
\approx
\frac{190.14}{20}
=9.51\ \mathrm{ms}.
$$
若模型在每个窗口结束后开始推理，并暂时忽略其他开销，则：

- 窗口开始阶段事件的最长响应时间约为
  $$
  400+9.51=409.51\ \mathrm{ms};
  $$
- 窗口内事件的平均响应时间约为
  $$
  200+9.51=209.51\ \mathrm{ms};
  $$
- 窗口末尾事件的响应时间接近 9.51 ms。

因此，下列三个时间具有不同含义：

| 数值 | 对应含义 |
|---:|---|
| 190.14 ms | 处理完整 8 s 事件流的总计算时间 |
| 约 9.51 ms | 平均处理一个 400 ms 窗口的计算时间 |
| 约 209.51 ms | 在简化假设下，一个事件从发生到获得预测的平均响应时间 |

其中，9.51 ms 和 209.51 ms 是根据完整样本 runtime 得到的粗略估计。正式报告在线延迟时，应当直接对每次模型更新进行同步计时，而不应只依靠除法推算。

### 3.4 固定事件数量与可变速率输入

固定时间窗口不是唯一的事件组织方式。

如果模型每次固定处理 $N$ 个事件，那么积累这些事件所需的时间取决于当前事件率 $R$：

$$
L_{\mathrm{accumulation}}
\approx
\frac{N}{R}.
$$
在事件活跃的场景中，$R$ 较高，相同数量的事件会在较短时间内到达；在静态或低事件率场景中，模型需要等待更长时间。因此，固定事件数量可以使单次计算规模更加稳定，却会引入可变的感知时间跨度。

CETUS 进一步根据事件率动态调整一次处理的事件数量。对于这种方法，仅报告一次 forward 的时间仍然不够，还需要同时报告：

- 一次更新平均处理多少事件；
- 这些事件覆盖多长真实时间；
- 每秒产生多少次预测；
- 输入时间跨度和计算时间的中位数及高分位数。

## 4. 为什么不同论文中的 runtime 不能直接比较？

下列方法都可能报告“10 ms runtime”，但这些数值对应的工作量可能完全不同：

| 处理方式 | 一次 runtime 所对应的输入 | 10 ms 的实际含义 |
|---|---|---|
| 完整事件流 | 完整 8 s 样本 | 10 ms 处理完 8 s 数据，吞吐率很高，但可能在 8 s 结束前无法输出 |
| 固定时间窗口 | 50 ms 或 400 ms 事件 | 每收集一个时间窗口后，需要 10 ms 完成一次更新 |
| 固定事件数量 | 例如 1024 个事件 | 处理 1024 个事件需要 10 ms，但这些事件覆盖的真实时间随事件率变化 |
| 可变速率事件流 | 动态数量、动态时间跨度 | 10 ms 是某种场景下的一次更新耗时，需要结合输入规模和时间跨度解释 |
| 逐事件更新 | 单个新事件或局部子图 | 单次更新很小，但完整事件流可能需要执行大量更新 |

因此，公平比较需要先统一比较单位。至少应当分别回答：

1. 处理相同真实时长的事件流需要多少总计算时间？
2. 每次输出建立在多长时间、多少事件的输入上？
3. 从事件发生到预测可用需要等待多久？

一次 forward 不能作为跨 representation 的唯一比较单位。

## 5. 相关事件视觉论文如何讨论效率与延迟？

### 5.1 代表性做法

| 方法 | Event representation 与调度方式 | 效率或延迟报告方式 | 对本文的启示 |
|---|---|---|---|
| RED | 将固定 50 ms 事件转换为稠密 Event Volume | runtime 包含事件预处理和检测器推理 | 固定窗口方法除了计算时间，还具有由窗口长度决定的事件积累时间。 |
| RVT | 将固定 50 ms 事件离散为具有多个时间 bin 的事件张量 | 报告 batch size 1 的 forward time 和参数量，并比较 eager 与编译版本 | 同一模型在不同编译方式和硬件上的 runtime 差异明显，说明 runtime 高度依赖实现环境。 |
| GET | 按时间和极性将事件组织成 Group Tokens | runtime 包含 event conversion 和 inference，并单独比较多种 representation 的构建时间 | Event representation 的构建可能占据显著开销，不能只测网络 forward。 |
| SAST | 基于固定 50 ms voxel representation 的动态稀疏 Transformer | 报告参数量、总 FLOPs、attention FLOPs 和 GPU runtime；动态 FLOPs 在多个样本上取平均 | 动态计算量随场景稀疏度变化；低 FLOPs 不一定带来同等幅度的 runtime 降低。 |
| EV-SpSegNet | 将完整 8 s 事件流表示为稀疏点云并一次处理 | 报告完整 8 s 样本的处理时间 | 该数值体现完整事件流的处理吞吐率，但不能直接代表实时响应延迟。 |
| CETUS | 直接处理事件流，并根据事件率动态调整一次输入规模 | 分解 window latency、inference latency 和 total latency | 可变速率方法需要同时报告事件数量、输入时间跨度和计算时间。 |
| AEGNN | 将事件表示为动态时空图，并在新事件到达时更新受影响的局部子图 | 报告逐事件异步更新的 FLOPs 和计算延迟 | 逐事件处理可降低积累延迟，但效率依赖异步执行方式和目标硬件。 |
| DAGr | 将事件组织成动态事件图，并进行异步局部更新 | 区分 perceptual latency、computational latency 和数据传输延迟 | 完整的端到端分析应同时考虑输入等待、计算和传输。 |
| STARE | 上一轮推理结束后立即从连续事件流中读取最新事件 | 使用 continuous sampling 和 latency-aware evaluation，将预测与实际输出时间对齐 | 忽略感知延迟可能高估在线性能，甚至改变不同方法的排名。 |

### 5.2 文献反映出的总体趋势

早期事件检测论文通常采用固定时长的 event frame 或 voxel representation，并报告每个时间片的 forward time。此类结果主要反映网络在特定输入形状下的计算速度，通常没有完整讨论事件积累等待时间。

后续工作开始将表示构建、模型推理、参数量和 FLOPs 放在一起讨论。GET 明确将 event conversion 纳入 runtime；SAST 则进一步说明动态稀疏模型的计算量会随输入变化，并且理论 FLOPs 与真实 GPU runtime 并不总是一致。

近期的流式方法更关注在线响应。CETUS 将输入积累时间和模型推理时间分开，DAGr 区分感知延迟与计算延迟，STARE 则进一步把预测真正可用的时间纳入精度评估。这一趋势说明，单一 runtime 已经不足以完整评价事件模型的实时性。

## 6. 不同 Event Representation 对效率和延迟的影响

### 6.1 Event count 和 event frame

Event count 或 event frame 通常将一个固定时间窗口内的事件累积到二维图像中。其特点是：

- 必须等待窗口结束，因此具有明确的事件积累延迟；
- representation 构建相对简单；
- 可以直接使用成熟的二维 CNN 或 detector；
- 模型计算量主要由图像分辨率决定，与实际事件数量的关系较弱；
- 即使大部分像素没有事件，稠密网络仍然会处理完整图像。

这类方法的 forward time 通常较稳定，但固定窗口会重新引入类似帧相机的离散输出节奏。

### 6.2 Voxel representation

Voxel representation 在空间维度之外保留若干时间 bin，比 event count 保存更多粗粒度时间信息。其效率受到下列因素影响：

- 事件积累窗口的长度；
- 时间 bin 数量；
- 传感器空间分辨率；
- 使用稠密算子还是稀疏算子；
- active voxel 的数量。

稠密 voxel 网络的计算量通常与 $B\times H\times W$ 相关，其中 $B$ 为时间 bin 数。稀疏 voxel 网络可以避免处理空 voxel，但需要额外的索引和稀疏算子调度开销。

### 6.3 Point representation

Point representation 直接保留单事件的空间位置和时间戳，避免早期稠密化，但其计算量通常更依赖输入事件数量。主要开销包括：

- 邻域搜索；
- 点排序或分组；
- 点采样；
- 局部特征聚合；
- 长事件序列的状态更新。

在固定时间窗口下，不同场景产生的事件数量不同，因此 point method 的 runtime 可能随事件率显著变化。只报告所有样本的平均 runtime 可能掩盖高事件率场景中的尾部延迟。

### 6.4 Raw event stream

Raw stream 方法可以使用较小的事件批次连续更新模型，从而减少等待大窗口结束的时间。但这种方式也带来新的成本：

- 更新次数明显增加；
- 每次输入规模较小，GPU 并行利用率可能降低；
- 需要维护历史状态；
- 如果当前更新尚未完成，新事件会进入队列并产生排队延迟；
- 可变事件率会同时影响输入时间跨度和计算负载。

因此，stream method 不一定具有最低的完整事件流处理时间，但可能具有更好的在线响应能力。

### 6.5 异步图网络和 SNN

异步图网络或 SNN 可以只更新受新事件影响的局部状态，在神经形态硬件或专用异步实现上具有潜在的低延迟和低能耗优势。但普通 GPU 擅长规则的批量计算，因此 GPU runtime 未必能够反映这些方法在目标硬件上的真实性能。此类方法通常还需要报告：

- 每事件或每时间步的更新成本；
- 每秒运算量；
- 目标硬件上的能耗和功率；
- 一次预测需要多少个事件或时间步。

## 7. 建议采用的效率评估框架

### 7.1 第一层：固定事件流时长下的吞吐效率

所有方法处理相同的 8 s 原始事件流，并报告：

| 指标 | 含义 |
|---|---|
| Processing time | 处理完整 8 s 事件流所需的总时间 |
| Real-time factor | 事件流真实时长除以处理时间 |
| Event throughput | 每秒能够处理的事件数量，建议使用 Mevents/s |
| Parameters | 模型参数量 |
| Peak GPU memory | 推理过程中的峰值显存 |
| Number of updates | 处理完整 8 s 事件流执行了多少次模型更新 |

建议使用如下表格结构：

| Method | Event Rep. | Scheduling | Input unit | Updates / 8 s | Processing time | RTF | Mevents/s | Params | Peak memory |
|---|---|---|---|---:|---:|---:|---:|---:|---:|
| HLC² | Points | Fixed duration | 400 ms | 20 | 190.14 ms | 42.1 | 待测 | 待测 | 待测 |
| RVT | Voxel grid | Fixed duration | 50 ms | 160 | 待统一测量 | 待测 | 待测 | 待测 | 待测 |
| SAST | Voxel grid | Fixed duration | 50 ms | 160 | 待统一测量 | 待测 | 待测 | 待测 | 待测 |
| CETUS | Raw stream | Variable rate | Variable | 待测 | 214.60 ms | 待计算 | 待测 | 待测 | 待测 |
| EV-SpSegNet | Points | Full stream | 8 s | 1 | 45.46 ms | 待计算 | 待测 | 待测 | 待测 |

该表衡量的是完成相同工作负载的计算效率，而不是在线响应速度。

### 7.2 第二层：每次预测的在线响应能力

在线实验应按照事件时间戳顺序重放测试事件流，并记录每次模型更新的输入和输出时间。建议报告：

| 指标 | 含义 |
|---|---|
| Input temporal span | 一次模型输入覆盖的真实时间跨度 |
| Events per update | 一次更新包含的事件数量 |
| Representation time | 构建当前输入表示所需的时间 |
| Forward time | 本次模型推理时间 |
| Output rate | 每秒产生多少次预测 |
| Response latency | 事件发生到预测可用的时间 |
| Queueing delay | 因上一轮推理尚未完成而产生的等待时间 |

建议使用如下表格结构：

| Method | Scheduling | Input span | Events/update | Rep. time | Forward time | Output rate | Response latency |
|---|---|---:|---:|---:|---:|---:|---:|
| HLC² | Fixed duration | 400 ms | Variable | 待测 | 待测 | 2.5 Hz | 待测 |
| RVT | Fixed duration | 50 ms | Variable | 待测 | 待测 | 20 Hz | 待测 |
| SAST | Fixed duration | 50 ms | Variable | 待测 | 待测 | 20 Hz | 待测 |
| CETUS | Variable rate | 报告中位数和 p95 | 报告中位数和 p95 | 待测 | 待测 | 待测 | 待测 |
| EV-SpSegNet | Full stream | 8 s | Full sample | 待测 | 待测 | 0.125 Hz | 不适用于低延迟在线输出 |

对于输入规模可变的方法，建议同时报告 median 和 p95，而不是只报告平均值。p95 可以反映高事件率或复杂场景中的尾部延迟。

### 7.3 第三层：精度与延迟的权衡

HLC² 已经具有不同 window duration 下的消融结果，可以进一步解释为精度与在线响应之间的权衡。

下表中的每次更新时间和响应延迟均由完整 8 s 样本 runtime 粗略估算，仅用于说明分析思路：

| Window duration | Updates / 8 s | Processing time / 8 s | Approx. compute/update | Approx. mean response | Approx. maximum response |
|---:|---:|---:|---:|---:|---:|
| 50 ms | 160 | 971.35 ms | 6.07 ms | 31.07 ms | 56.07 ms |
| 100 ms | 80 | 538.86 ms | 6.74 ms | 56.74 ms | 106.74 ms |
| 200 ms | 40 | 325.57 ms | 8.14 ms | 108.14 ms | 208.14 ms |
| 400 ms | 20 | 190.14 ms | 9.51 ms | 209.51 ms | 409.51 ms |
| 800 ms | 10 | 118.51 ms | 11.85 ms | 411.85 ms | 811.85 ms |
| 1600 ms | 5 | 80.56 ms | 16.11 ms | 816.11 ms | 1616.11 ms |

这组结果反映出两个相反趋势：

1. 较长窗口减少更新次数，因此处理完整 8 s 事件流所需的总计算时间更短；
2. 较长窗口增加事件积累等待时间，因此在线响应速度更慢。

例如，400 ms 窗口获得当前最好的 IoU，但 50 ms 窗口将估计平均响应时间从约 209.51 ms 降低至约 31.07 ms，同时 IoU 仅从 90.45% 降至 89.70%。这说明 HLC² 可以根据应用需求选择不同工作点：

- 400 ms：精度优先配置；
- 50 ms 或 100 ms：低延迟配置；
- 更长窗口：吞吐率优先，但在线响应较慢。

正式论文中应使用直接测量的 per-update latency 替代上述估计值。

## 8. 建议的统一计时协议

为了使实验可复现并减少 reviewer 对公平性的质疑，建议明确以下设置：

1. 所有方法使用 batch size 1；
2. 使用相同 GPU、CUDA、PyTorch 和精度设置；
3. 在正式计时前执行充分的模型 warm-up；
4. GPU 计时前后调用同步操作，避免异步执行造成低估；
5. 明确磁盘 I/O 是否排除；
6. representation construction、CPU-to-GPU transfer 和 post-processing 应分别计时，并同时给出端到端总时间；
7. 所有方法处理相同的原始事件样本；
8. 对每个测试样本分别计时，报告 median、mean 和 p95；
9. 对 point、voxel 和 stream 方法记录每个样本的事件数；
10. 对可变输入方法记录每次更新覆盖的事件数量和真实时间跨度。

如果篇幅有限，可以在主文中报告端到端 processing time、RTF、Params 和 peak memory，并将详细时间分解放在补充材料中。

## 9. 对当前论文写作的建议

### 9.1 建议的章节名称

可以新增一个小节：

> **Computational Efficiency and Online Latency**

该小节先解释完整事件流处理时间，再讨论不同输入调度方式产生的在线延迟。

### 9.2 对当前 runtime 的重新表述

当前 SOTA 表格中的 `Runtime (ms)` 建议改为：

> **Processing Time (ms / 8-s Stream)**

并在 metric 或 implementation details 中说明：

> Processing time measures the end-to-end computation required to process a complete 8 s event stream and therefore reflects computational throughput rather than per-output online latency.

这句话的中文含义是：

> Processing time 表示处理完整 8 s 事件流所需的端到端计算时间，因此衡量的是计算吞吐效率，而不是单次预测的在线响应延迟。

### 9.3 建议强调的核心观点

论文中的效率讨论可以围绕以下逻辑展开：

1. 不同 event representation 具有不同的输入构建成本；
2. 不同方法的一次模型调用覆盖的事件数量和真实时间跨度不同；
3. 完整事件流处理时间可以比较总体吞吐率；
4. 输入积累时间、计算时间和输出频率共同决定在线响应能力；
5. HLC² 在 400 ms 设置下具有较高的事件流处理吞吐率；
6. window duration 消融进一步显示，HLC² 可以通过缩短窗口在有限精度损失下显著提高输出频率并降低响应延迟。

## 10. 结论

模型效率不能由单一 runtime 完整描述。对于事件视觉方法，至少需要区分：

- **完整事件流处理时间**：衡量处理相同感知时长所需的总体计算成本；
- **单次更新计算时间**：衡量模型完成一次状态更新或预测所需的计算时间；
- **事件积累时间**：衡量形成一次模型输入需要等待多长真实时间；
- **在线响应延迟**：衡量事件发生到对应预测可用的总时间；
- **输出频率**：衡量系统每秒能够产生多少次新预测。

对于 HLC²，当前的 190.14 ms 应解释为处理完整 8 s 事件流的总时间，而不是在线响应延迟。基于不同 window duration 的现有实验，可以进一步构建精度、吞吐率和响应延迟之间的权衡分析。这样的效率讨论不仅更严谨，也能够更清楚地说明 HLC² 在不同实际部署需求下的适用方式。
